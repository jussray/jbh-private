# Project Sovereignty Contract

This private operations project must preserve its core product meaning, supplier/commercial truth, approval boundaries, and critical operating capability if an external provider, API, SDK, model, connector, runtime, sibling project, or vendor disappears or materially changes.

## Invariants

- **Human authority comes first.** Authorized humans are the root of consequential authority. Models, agents, providers, workflows, evidence, learned knowledge, fingerprints, proof cookies, and automations may inform or constrain a proposal but may not manufacture, renew, widen, or replay authority.
- Human authority does not rewrite reality. Approval can authorize an action; only evidence can support a truthful execution, supplier, pricing, purchase, refund, deployment, or commercial outcome claim.
- Project-owned contracts define canonical inputs, outputs, errors, authority, state, evidence, private-data meaning, and completion semantics.
- External providers and sibling projects are adapters/capabilities, not project identity.
- Critical dependencies are `REPLACEABLE`, `DEGRADED_FALLBACK`, `HARD_DEPENDENCY`, or `UNKNOWN`.
- Critical capability needs an alternate adapter, local/open implementation, deterministic fallback, export/manual recovery path, or honest safe degraded mode unless a documented hard dependency is explicitly accepted.
- Critical private and commercial data keeps project-owned semantics and a migration/export path.
- Provider swaps must not broaden authority, replay stale approvals, duplicate mutations, expose private data, or weaken evidence requirements.
- Provider outcomes map into project-owned receipts; provider acceptance is not business outcome proof.
- When operated through Founder Control Room, this remains a sovereign subsystem, not a separate founder OS.

## World as experience and knowledge

Legitimate real-world interaction may become evidence-bearing experience: supplier responses, order behavior, pricing observations, customer evidence, storefront results, analytics, runtime behavior, provider responses, experiments, repository history, operational failures, and verified outcomes.

```text
World → observation → provenance → evidence classification → experience receipt → knowledge candidate → contradiction / red-team check → context + confidence + freshness → working knowledge → proposal → authorized action when applicable → outcome evidence → new experience
```

Experience is not automatically truth. One vendor response, price observation, transaction, analytics spike, or customer message is not automatically a durable rule. Working knowledge must remain scoped, provenance-backed, challengeable, freshness-aware, and supersedable.

## Private-operations boundary

World-derived knowledge may inform supplier evaluation, pricing proposals, commercial planning, operational fixes, or customer-support proposals. It does not create vendor-contact, purchase, pricing, refund, customer-contact, provider, database, deployment, credential, or merge authority. Private data, commercial approvals, and production mutation remain separately gated.

## Mandatory audit questions

> If every named provider or sibling project disappeared now, what stops, what survives, what is the recovery path, and what evidence proves it?

> What experience is this system learning from, what would falsify the conclusion, and who holds authority for the next consequential commercial action?

Architecture docs are not failover or learning proof. Verify contract, adapter, focused test, runtime, private-data boundary, data-exit path, authority, and real-world evidence separately.

Use: Reality → ULTRATHINK → Red Team 1 → Lindy → L99 → OODA → smallest reversible implementation → focused proof → Red Team 2 / provider-loss + knowledge-corruption attack → Documentation Truth → rollback → next gate.
