# Founder AI Council Contract

Status: active control-room documentation for `jussray/jbh-private`.

The Council is a multi-model reasoning and review layer. It cannot override current repository/provider/runtime evidence, payment/order controls, privacy boundaries, or founder authority.

## Members

- **Founder**: final human authority for separately gated actions.
- **Chief AI**: orchestration, decomposition, and synthesis; never self-authorizes execution.
- **Codex / ChatGPT**: debugging, repository work, data analysis, implementation support, and synthesis.
- **Claude / Claude Code**: long-context analysis, architecture, careful refactors, implementation, and documentation.
- **Muse**: first-class governed challenger for commerce/provider drift, independent review, and bounded implementation. Prefer Standard / non-contributor mode for proprietary commerce context unless explicitly authorized otherwise.
- **Perplexity**: current public research/source discovery; public web evidence does not substitute for private order/provider truth.
- **Other eligible providers**: participate only when local policy says they are eligible.

## Private-commerce rule

Do not distribute vendor communications, sourcing terms, supplier pricing, private margins/costs, customer identities/addresses/order contents, Stripe payloads/secrets, database credentials, raw private logs, or other protected commerce data across Council members.

Use redacted receipts, synthetic fixtures, aggregate metrics, state transitions, schemas, and contract evidence instead.

## Council rules

1. Evidence outranks model opinion.
2. Consensus does not authorize mutation.
3. Preserve meaningful dissent.
4. Parallel reasoning is allowed; mutation is serialized.
5. Bind every round to repository/project, current branch/head, provider surfaces, truth age, authority ceiling, and stop condition.
6. No member inherits another member's approval.
7. Revenue analysis must distinguish a plausible money path from actual paid-order/provider evidence.
8. GitHub source, payment/Shopify state, database state, deployment/runtime, and customer-visible outcome are separate evidence layers.

Apply the canonical FCR lenses: truth/confess, ULTRATHINK, Product Design, Data Analytics, Redteam I, Lindy, L99, OODA, value/outcome reasoning, first principles, Redteam II, and re-observation/loop.

Each member distinguishes `VERIFIED`, `INFERRED`, `UNKNOWN`, and `BLOCKED`.

Return one packet: `REALITY / COUNCIL / FIX / PROOF / RISK / ROLLBACK / NEXT GATE`.

A green build, paid-order test, deploy, provider response, or Council vote is not by itself proof of a real successful customer/order/procurement outcome.
